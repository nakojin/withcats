# 여행 자료 v2 기획안 (초안)

기준일: 2026-10-10 · 대상: korea-travel(321) · japan-travel(130) · china-travel(75) · 브랜치 `claude/new-git-repository-bzoc4t`

## 1. 한 줄 목표

이용자가 관광지를 고르면 **그 장소의 쓸 만한 설명·이동·운영 정보와, 근처에서 먹고 자고 즐길 거리**를 한 번에 본다. v1은 "장소 목록의 뼈대"이고, v2는 "사이트가 그대로 쓰는 데이터"다.

핵심 진단은 두 가지다.
1. **폭이 좁다.** 일본은 도쿄 4, 오사카 3, 후쿠오카 2, 오키나와 5곳이다. 중국은 거점이 11곳이다. "한국인이 많이 가는 곳" 기준으로는 부족하다.

## 3. v2 데이터 모델 (3개국 공통 스키마)

지금은 나라마다 필드명이 다르다(`records`/`items`, `operational`/`hours_and_fees`/`operations`). v2는 하나로 맞춘다.

| 블록 | 필드 | 규칙 |
|---|---|---|
| 식별 | id, country, admin_region, city, 이름(ko/현지어/영문) | 한국은 v1.1의 `admin_region` 재사용 |
| 위치 | lat, lng, geo_type(point/area), precision, geo_source, address | 넓은 장소(한라산·거리)는 area + 대표 진입점 |
| 소개 | summary(1~2문장), description(300자 이상), highlights(4개 이상) | 출처 문장을 그대로 베끼지 않고 한국어로 요약 |
| 이용 | recommended_duration_min, best_time, how_to_get_there, tags(카테고리·동행·계절) | 소요시간·접근은 공식 안내 근거 |
| 운영 | hours, fees, reservation, closed_days, payment, foreign_visitor_notes | 항목별 상태 confirmed / unconfirmed / n_a와 확인일 |
| 근거 | sources[](url, 확인일, 뒷받침한 항목) | 값마다 출처 연결 |
| 품질 | depth_tier(A/B/C), last_verified | 사이트에 신뢰도 배지로 노출 |
| 주변 | nearby[](poi_id, type, distance_m) | 별도 `pois` 컬렉션 참조 |

원칙은 지금과 같다. **확인 못 한 값은 null + 이유를 남기고 추정으로 채우지 않는다.**

## 4. 단계별 계획

| 단계 | 내용 | 산출물 | 합격 기준 |
|---|---|---|---|
| P0 설계 | v2 스키마 확정, 검증기(validator), 파생물 자동 생성 스크립트 | schema v2, `build` 스크립트 | v1 → v2 변환 후 정보 손실 0, md·index·catalog 자동 일치 |
| P1 좌표 | 526곳 좌표·정밀도 부여 | lat/lng/precision | 지역 경계 검사 통과, 2개 출처 대조, 표본 10% 수작업 확인 |
| P2 깊이 보강 | Tier A부터 설명·소요시간·접근 확충 | description 300자+, highlights 4+ | 값마다 공식 출처, 분량 기준 충족 |
| P3 폭 확대 | 일본·중국 인기 지역 장소 추가 | 일본 130→약 300, 중국 거점 확대 | 선정 근거 기록, 중복·관계 검토 |
| P4 운영정보 | 중국 요금·예약·결제, 한국 시간·요금·예약 | 운영 블록 채움 | 공식 페이지 직접 열람분만 반영 |
| P5 주변 시설 | 파일럿 지역 1곳 후 확대 | `pois` 컬렉션 | 출처·라이선스 확정 후 진행 |
| P6 사이트 연동 | 정적 JSON 내보내기, 변경 이력 | places.json, pois.json, CHANGELOG | 스키마 검증 통과, 버전 태그 |

### 좌표(P1) 시험 결과
OSM Nominatim으로 8곳(국가별 2~3곳)을 시험했다. 8곳 모두 좌표가 나왔지만 **첫 결과가 관광지 본체가 아닌 경우**가 있었다(다카오산은 역, 한라산은 산 중심점). 그래서 `precision`과 `geo_type`을 두고, 경계 검사와 2차 출처 대조를 거치는 방식을 권한다. 한국 TourAPI(apis.data.go.kr)는 이 환경에서 응답이 없고 서비스 키도 필요하다.

### 작업량 추정
이번에 일본 28곳 보강에 에이전트 토큰 약 40만이 들었다(장소당 약 1.4만). 같은 방식으로 526곳 전체를 깊이 보강하면 약 760만 토큰이다. 그래서 **Tier A(인기·핵심 약 150곳) 먼저**, 나머지는 후속 릴리스로 나누는 것을 권한다.

## 5. 이용자 관점의 기능 (v2 데이터가 가능하게 하는 것)

1. 지역 → 관광지 목록, 필터(소요시간·계절·카테고리·무료/유료·예약 필요).
2. 지도와 "여기서 가까운 곳" 정렬(좌표 필요).
3. 방문 전 체크리스트: 예약·결제수단·여권 필요 여부(특히 중국).
4. 반나절·하루 코스 후보(소요시간과 거리로 묶기).
5. 장소 선택 시 주변 음식점·카페·숙박·즐길거리.
6. 신뢰도 표시: "공식 확인 N일 전", 확인 못 한 항목은 회색으로 표시하고 공식 링크 제공.

## 6. 품질 게이트

- 모든 값에 출처 URL과 확인일. 확인일이 90일을 넘으면 사이트에 재확인 표시.
- 좌표는 해당 시도·도현·성 경계 안에 있어야 한다.
- 파생물(md, index.html)은 수작업이 아니라 빌드 스크립트로만 생성한다. 이번 일본 작업에서 렌더러를 임시로 만들었으니 정식화한다.
- 한 번에 한 나라씩 커밋하고, 커밋마다 검증 결과를 남긴다.

## 8. 확정 사항 (2026-10-10)

1. **우선순위**: Tier A(인기·핵심 약 150곳)의 깊이 보강을 먼저 하고, 이어서 일본·중국 폭 확대로 간다.
2. **인기 지역 판단**: 한국인 방문이 많은 일본·중국 지역은 웹검색 결과에서 추출한다. 검색 근거(질의·URL·확인일)를 `travel-common/research/`에 남긴다.
3. **데이터 수집 원칙**: 공식 정보와 리뷰는 **복제가 아니라 정보 수집**으로 쓴다. 사실·수치(위치, 가격대, 대표 메뉴, 영업 형태 등)를 뽑아 우리 문장으로 요약하고, 원문·리뷰 문장을 그대로 옮기지 않는다. 모든 항목에 출처 URL과 확인일을 남기고, 평점·리뷰 수 같은 값은 "참고 지표"로 출처와 함께 표시한다.
4. **진행 방식**: P0(스키마·검증기)와 P1(좌표)부터 시작한다.
5. **저장소 운영**: 이 기획안을 `docs/`에 두고 작업과 함께 갱신한다. 단계가 끝날 때마다 7절 표와 9절 진행 현황을 고친다.

### Tier A 선정 방법
1. 웹검색으로 한국인 인기 일본·중국 지역과 대표 명소를 모아 후보 목록과 근거를 만든다.
2. 기존 526곳 가운데 후보와 겹치는 곳을 Tier A로 표시하고, 없는 곳은 신규 후보로 올린다.
3. 한국은 시도마다 최소 4곳 이상 대표 명소가 들어가도록 지역 균형을 맞춘다.
4. 목록은 사용자 검토를 거쳐 확정한 뒤 깊이 보강에 들어간다. (선정 결과는 `travel-common/tiers/`에 둔다.)

## 10. 오픈 이슈

- 사이트 기술 스택 미정: 정적 JSON 내보내기를 기본으로 한다.
- 중국 공식 사이트 접속 가능 여부는 P4 시작 전에 확인한다.
- 주변 시설(POI)은 5절 기능 기준으로 파일럿 지역 1곳을 정한 뒤 시작한다. 리뷰 사이트는 사실·수치 수집만 하고 문장을 복제하지 않는다.
